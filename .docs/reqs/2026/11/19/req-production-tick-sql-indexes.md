# 制作调度节拍的 SQLite 查询不再扫描故事全文

## 问题

上一项改动（`production-tick-content-rev`）去掉了节拍把故事全文复制到 JavaScript 的开销，但 SQLite 内部仍有大量工作：在实际书库副本上，一个节拍约 164 ms，几乎全部在 SQLite 中。

- 判断“是否有更新版本”的条件（`supersededSql`）对每个候选故事在同一用户的全部故事中逐篇解析 `document` 取修订根和版本号；后台需求查询每秒约 87 ms。
- 横图重绘检查对全部已完成的故事解析 JSON（约 36–46 ms）。
- 按 `generation_control`、`generation_mode`、`state`、`lock_until` 过滤故事时，这些列位于 `document` 之后，SQLite 需要沿每篇故事的溢出页读到它们（每次全表扫描约 12–16 ms）。

## 目标

节拍中的故事查询由索引回答，不再逐篇解析故事 JSON 或沿溢出页读取故事行；查询结果和制作规则不变。

## 验收标准

- [ ] 判断是否有更新版本时，同一家族的版本查找由索引直接回答，不解析其他故事的 `document`。
- [ ] 一个节拍内执行的每条故事查询都不对 `stories` 做全表扫描（只允许按索引查找或扫描覆盖索引）。
- [ ] 在实际书库副本上，内容未变时一个节拍在 SQLite 中的耗时从约 164 ms 降到 5 ms 以内。
- [ ] 故事写入耗时不因新增索引明显增加（平均大小与最大故事的局部写入耗时与改动前相当）。
- [ ] 所有查询结果不变：现有制作、版本、横图、恢复相关测试全部通过。
- [ ] 若以后修改修订根或版本号的 SQL 表达式而未同步索引，测试会失败而不是静默变慢。
- [ ] 升级沿用已验证的整库备份和迁移流程；`latestMigration` 更新；`schemaVersion` 不变，支持当前格式的旧版应用仍可打开书库。

## 约束

- 只新增索引，不修改现有查询语句和制作规则。
- 测试使用隔离数据，不触碰用户书库。

## 非目标

- 将提示词记录移出 `document`。
- 节拍以外的按需路径（打开故事、导出等）的性能。
