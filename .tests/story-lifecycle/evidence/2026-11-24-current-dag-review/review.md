# Production DAG and story lifecycle review · 24 November 2026

**Hold sign-off on the production workflow.** Ordinary creation, review, rendering and single-frame recovery have working paths. A revision can discard the identity of failed work, buy the same work again on Continue, and leave a fully illustrated story marked failed. This was reproduced on both the published 0.15.0 source tag and current source.

The release baseline is `v0.15.0` (`46809ae0`, format 2). The current test copy contains the working changes on `70690f69`, subsequently committed as `69495ab8` (format 3). Compared with that commit, all changed application and test files match byte for byte. One implementation-plan document changed after the copy was taken. Tests used macOS, Node 24.22.1, temporary SQLite libraries and controlled provider responses. Browser evidence is from the ChatGPT in-app browser against the real reader and an isolated local server. The recommendation concerns workflow correctness, independent of generated artwork quality.

## Findings

| Priority | Trigger and observed outcome | Repair and acceptance condition |
| --- | --- | --- |
| P1 | **A failed visual batch loses all its frame keys on revision.** Fail a four-frame visual call, pause, change only the acceptance requirement and save. Preview counts one carried fault. The parent lists four concrete visual targets. The child lists one visual target with an empty key and no page. Continue alone calls the visual generator again. Same result on both builds. | Carry the unchanged node, instance key and bound inputs for every failed target. Continue may run independent work. | P1 | **Failed acceptance registration loses its recovery requirement.** Fail the registration of two acceptance items, pause, change only the art style and save. Revision saving strips that payload, tests each nonempty key against frame order, then inserts one node/key pair for the child. A batch record uses an empty key. This explains both the duplicate work and the surviving untargeted fault. **Triage of the eleven ordinary failures.** The seven in the 47-file run recurred in a focused, serial run. Two expect a second paid draw after restoring a readable file. Production correctly reuses the file. One supplies an empty payload for the purported valid DAG job in an orphan-containment test. One expects a preparation call held before paid send to finish after Pause. In a diagnostic rerun, Resume finished preparation with every draft setting preserved. One observes the compatibility field as paused after replaying a revision. SQLite and `lifecycle.control` both read active, while `continuation` remains true. One attempts Resume on an already-active failed story and receives the lifecycle's 409. The seventh is the queued preparation receipt in the findings above. Four additional synopsis tests also stop at an already-active Resume with 409, before reaching their synopsis assertions. Those paths need valid test preconditions. Their current red results do not establish a synopsis-generation defect.

**80-frame completion.** The base run skipped the heavy case. Its full-tier rerun exceeded the registered 60-second deadline. A diagnostic rerun with a 180-second deadline reached completion in 72.1 seconds with four storyboard batches, 80 distinct drawings and all 80 images ready. The published timeout is a reproducible test risk on this machine. This case eventually completes.

**What improved since the earlier audit.** Current production regressions pass for an equivalent edit while a draw is leased (C010), the correct running frame beside a different failed frame (C011), the running-state reply to rename (C013, API), exhausted review repair and authorization (C014), matching lost images after replan including duplicate-input frames (C015), and scoped skipping of failed review with a complete draft (C017, API). These results qualify the older failed ledger entries at the service layer. Browser confirmation of all six on this build remains open.
